# ÉLAIRE — страница выбора услуг (React + сервер)

Учебный пример: одна страница сайта салона красоты на React.
Только выбор услуг. Данные приходят с локального имитационного
сервера — плагина Vite. Других экранов нет.

Используется на лекции, чтобы показать, как React-страница
работает с сервером: запросы через `fetch`, состояния загрузки
и ошибки, разделение данных и отображения.

---

## Как запустить

Нужен **Node.js** версии 18 или выше и **npm**.

```bash
node --version
npm --version
```

Если команды не найдены — установите Node.js с [nodejs.org](https://nodejs.org).

Дальше:

```bash
npm install     # установить зависимости (один раз)
npm run dev     # запустить dev-сервер
```

Vite напишет адрес — обычно `http://localhost:3000`.
Откройте его в браузере.

Другие команды:

```bash
npm run build     # собрать продакшн-версию в dist/
npm run preview   # посмотреть собранную версию
```

## Что внутри

Одна страница: слева список категорий, справа — услуги выбранной
категории. Сверху индикатор шагов, снизу — подвал.

**Что работает:**

- **Загрузка категорий с сервера** при открытии страницы.
  Пока данные идут — показывается «Загрузка…».
- **Клик по категории в сайдбаре** — категория подсвечивается,
  справа появляется список её услуг. Услуги тоже грузятся
  с сервера, при каждой смене категории.
- **Заглушки**: «Загрузка услуг…» пока грузятся, сообщение
  об ошибке, если запрос упал, «В этой категории пока нет услуг»,
  если список пустой.

**Что не работает:**

- Кнопки «Назад», «Выбрать», «Войти» — обработчиков нет.
- Переходы на другие страницы — страница одна.
- Формы и отправка данных — не реализованы.

## Сервер

Сервер — это **плагин Vite**. Он перехватывает запросы к `/api/*`
и отдаёт JSON. Всё остальное пропускает к Vite — чтобы отдавались
HTML, CSS, JS и картинки.

Подключён в `vite.config.js`:

```js
import apiMiddleware from "./server/server.js";

export default defineConfig({
  plugins: [apiMiddleware()],
  server: { port: 3000 },
});
```

### Эндпоинты

| Метод | URL | Что возвращает |
|---|---|---|
| GET | `/api/categories` | Список категорий: `[{ id, name, servicesCount }]` |
| GET | `/api/categories/:id/services` | Услуги одной категории: `[{ id, title, desc, duration, price }]` |

Проверить их можно прямо в браузере:

```
http://localhost:3000/api/categories
http://localhost:3000/api/categories/1/services
```

### Задержка 1000 мс

В `server.js` для эндпоинта услуг стоит:

```js
setTimeout(() => { ... }, 1000);
```

Это **специально** — чтобы на клиенте было видно состояние «Загрузка…».
В реальном проекте задержка появляется сама собой из-за сети.
Здесь мы её имитируем, чтобы студенты видели, что заглушка работает
не зря.

### Что можно менять в сервере

- **Данные** — все категории и услуги лежат в `server/database.js`.
  Правь там, не в `server.js`.
- **Задержку** — число `1000` в `setTimeout`. Поставь `0`, чтобы
  ответы приходили мгновенно.
- **Порт** — в `vite.config.js`.

## Клиент

### Как устроены запросы

Все запросы к серверу собраны в `src/api.js`:

```js
export async function fetchCategories() { ... }
export async function fetchServicesByCategory(categoryId) { ... }
```

Компоненты **не знают** про `fetch`, URL и JSON. Они вызывают
функцию и получают данные или ошибку. Если завтра сервер переедет
на другой язык — правится только `api.js`.

### Два уровня загрузки

На странице **два независимых запроса**:

1. **Категории** — грузит `App` при открытии. Один раз.
2. **Услуги** — грузит `ServicesList` при каждой смене активной
   категории. По требованию.

Каждый запрос имеет свои состояния `loading` и `error`. Это сделано
сознательно: пока грузится категория — показываем одну заглушку;
пока грузятся услуги — другую.

### Схема потока данных

```
App
 ├─ грузит категории через fetchCategories
 ├─ хранит activeCategoryId
 │
 ├─► Sidebar ─── рендерит категории
 │   └─► CategoryItem ─── клик → onCategoryClick
 │
 └─► ServicesList
     ├─ грузит услуги через fetchServicesByCategory(activeCategoryId)
     ├─ хранит services, loading, error
     └─► ServiceRow ─── рендерит одну услугу
```

**Данные идут вниз через пропсы. События идут вверх через колбэки.**

## Что изменилось по сравнению с версией без сервера

Если вы уже видели предыдущий пример (где данные были захардкожены
в `App.jsx`), вот что поменялось:

### 1. Данные уехали на сервер

**Было:** массив `servicesData` прямо в `App.jsx`.
**Стало:** данные в `server/database.js`, клиент их запрашивает.

### 2. Появился `api.js`

Единственное место, где клиент знает про `fetch` и URL-адреса.
Компоненты вызывают `fetchCategories()` и не думают о деталях.

### 3. Появились состояния `loading` и `error`

**Было:** данные мгновенно доступны, никаких состояний.
**Стало:** три варианта отображения — «Загрузка…», «Ошибка…», «Данные».

### 4. `ServicesList` сам грузит услуги

**Было:** `App` передавал готовый массив `services` через пропс.
**Стало:** `App` передаёт только `activeCategoryId`, а `ServicesList`
сам делает запрос, когда категория меняется.

Почему так: иначе `App` раздувается — шесть состояний вместо трёх.
Логичнее держать логику загрузки там, где эти данные отображаются.

### 5. `CategoryItem` принимает `servicesCount` внутри `category`

**Было:** пропс `servicesCount` передавался отдельно.
**Стало:** число приходит с сервера прямо в объекте категории.
Клиенту не нужно знать про массив услуг, чтобы показать счётчик.

### Что не изменилось

- **`Header`, `Footer`, `StepIndicator`** — как были, так и остались.
- **`ServiceRow`** — принимает тот же объект услуги, ничего не знает
  про источник данных.
- **Стили** — те же самые.
- **Структура разметки** — та же.

## На что смотреть в коде

### `src/App.jsx`

- **Три состояния про категории:** `categories`, `loading`, `error`.
- **`useEffect` с `[]`** — запрос выполняется один раз при монтировании.
- **Автовыбор первой категории** после загрузки: `data[0]?.id || null`.
- **Ранние `return`** для случаев загрузки и ошибки.

### `src/api.js`

- **`try / catch`** вокруг каждого запроса.
- **Проверка `response.ok`** — `fetch` сам не падает при 404 или 500.
- **Проброс ошибки наверх** через `throw` — чтобы компонент её показал.

### `src/components/ServicesList.jsx`

- **Свои `loading`, `error`, `services`.**
- **`useEffect` с `[activeCategoryId]`** — при смене категории
  автоматически грузит новые услуги.
- **Три варианта рендера:** заглушка загрузки, сообщение об ошибке,
  список (или пустой список).

### `src/components/CategoryItem.jsx`

- **`category.servicesCount`** — число берётся прямо из объекта,
  а не считается в родителе.

## Что можно взять в свой проект

- **Схему «api.js + компоненты, которые не знают про fetch».**
- **Три состояния для каждого запроса:** loading / error / data.
- **Паттерн `<EmptyState>` и `<LoadingState>`** — две разные заглушки
  для разных ситуаций.
- **Разделение запросов по компонентам** — категории в `App`,
  услуги в `ServicesList`.

## Что тут не реализовано

Это учебный пример. Здесь нет:

- **Переходов** между экранами. Кнопки не работают.
- **Отправки данных на сервер** — только чтение.
- **Валидации форм** — форм нет.
- **Роутера** — страница одна.
- **Настоящей БД** — данные в памяти, при перезапуске сбрасываются.
- **Обработки ошибок сети** (когда сервер вообще недоступен) —
  сейчас ловится только HTTP-ошибка.

Всё это — темы для самостоятельной работы.

## Полезно знать

### Если что-то не грузится

1. Откройте DevTools → **Network** → фильтр `Fetch/XHR`.
2. Найдите запрос `/api/categories` или `/api/categories/.../services`.
3. Посмотрите **статус** — 200, 404, 500.
4. Посмотрите **ответ** — что вернул сервер.

Если в ответе `{ "error": "..." }` — сервер вернул ошибку, читайте
текст. Если запрос не появился вообще — значит, `fetch` не был вызван,
проблема в клиенте.

### Если сервер не отвечает

Проверьте, что `npm run dev` запущен и в терминале есть строка
`API Middleware загружен`. Если нет — сервер не поднялся, скорее
всего из-за ошибки в `server.js`.
